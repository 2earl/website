How we protect the 2earl account and the services that use it. This page is part of our data processing terms (technical and organizational measures, Art. 32 GDPR). The design and threat model are public in 2earl/login.

1. Where data is and how it’s stored

  • Account data is stored in Cloudflare D1 and Workers KV in Cloudflare’s EU jurisdiction.
  • All traffic uses TLS 1.2 or newer, with HSTS. There is no unencrypted access to any service.
  • Session cookies, access and refresh tokens, sign-in codes and directory tokens are stored only as hashes. Authenticator-app secrets and the details of app connections are encrypted. Passkeys are stored as public keys.
  • We store no passwords: 2earl doesn’t use them.

2. Signing in

  • Sign-in with Google, a one-time code by email, a passkey, or an organization’s single sign-on (SAML 2.0). Optional second factors: passkeys and authenticator apps, with recovery codes.
  • Sessions end after 12 hours unused and after 7 days at most. Sensitive changes ask for the second factor again.
  • Organizations can manage their accounts, require their single sign-on, and connect their directory (SCIM 2.0) so leavers lose access at once. For the accounts they manage, they can require a second factor or a passkey, shorten sessions, and limit the ways to sign in and the networks the accounts can be used from; every request is checked.
  • Apps get short-lived tokens bound to one service; we support proof-of-possession tokens (DPoP) and pushed authorization requests.

3. Who can access what

  • The only person with administrative access is the operator named in the imprint. Administration always requires a second factor.
  • Infrastructure credentials are scoped to what each task needs and kept as encrypted secrets in GitHub and HashiCorp Terraform Cloud; they never hold personal data.
  • Each 2earl service sees only the data its permissions allow.

4. How the software is built and shipped

  • All code is open source. Every change goes through a pull request with automated type checks, tests and code scanning (CodeQL).
  • Production deploys run only after the operator approves them. Infrastructure is managed as code, and changes are applied by hand after review.
  • Dependency updates are proposed automatically and reviewed before they ship.

5. Logging and abuse protection

  • A security log records sign-ins, changes to sign-in methods and second factors, administration and organization changes. It is kept for 90 days. Organizations see their own activity.
  • Rate limits at the network edge and in the service protect sign-in, codes, tokens and directory sync.
  • People get an email about every security-relevant change to their account.

6. Backups and availability

  • The database has point-in-time recovery for up to 30 days. Deleted data can stay in it until then; it is restored only to recover from a disaster.
  • The services run on Cloudflare’s global network. We don’t yet offer a contractual service level.

7. Incidents and breaches

We assess a suspected incident at once, contain it, and keep a record of it. We report personal data breaches to the supervisory authority within 72 hours where required (Art. 33 GDPR), tell affected people where the risk is high (Art. 34), and tell organizations about their managed accounts within 48 hours (data processing terms).

8. Subprocessors

Subprocessor What for Where
Cloudflare, Inc. Hosting, database, network, email delivery Data stored in the EU; requests handled at the nearest location

Google is not a subprocessor: when someone chooses to sign in with Google, Google acts as an independent controller for their Google account. An organization’s identity provider and directory are the organization’s own.

9. Reporting a vulnerability

Please report it privately through GitHub (Security, then “Report a vulnerability”) on 2earl/login, or write to legal@2earl.com. Don’t open a public issue. We acknowledge reports and fix confirmed issues as quickly as their risk demands.
